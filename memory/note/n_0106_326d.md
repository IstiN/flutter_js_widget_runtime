# Note: n_0106_326d

SWITCH LATENCY SOLVED (2026-10-30, commit 3e4fc7a): the 10-15s module switch hang in three_example was a DOUBLE DISPOSE of the same isolate QuickJS backend — fast dispose #1 from JsWidgetRuntimeWidget.didUpdateWidget restart path (_start's previous.dispose()), slow dispose #2 from the framework dispose() gate chain. The second _shutdownWorker sent 'shutdown' into an already-exiting isolate → no ack → 10s timeout → global _lifecycleGate held every subsequent boot (alternating switches stalled 10s; 'never loading' modules were the ones whose boot slot the stall ate). FIX: _shutdownWorker idempotent via _workerStopped latch + shared in-flight future. Post-fix measured: acked=false 0, engine dispose 0-17ms, firstFrame ~251ms per switch. Diagnosis method that cracked it: JSR_SWITCH_LOG=true dart-define instrumentation (JSSHUT/JSBOOT/GATE/ENGDSP with per-engine ids, app-side SWITCH sourceLoaded/firstFrame + JSR_THREE_AUTO=<ms> auto-cycler) on a RELEASE build run from terminal with window focus via osascript. Two artifacts of measurement to remember: (1) bool.fromEnvironment needs =true, ='1' is FALSE; (2) an UNFOCUSED macOS window throttles vsync — firstFrame readings of 4252ms were the focus artifact, not real; with focus firstFrame=251ms. Also: three-instancing-scatter/three-materials-matcap/three-materials-toon were missing from example/pubspec.yaml assets (wave-3 agents added widgets+enum but not asset lines) — 'widget does not load' with NO error in logs = check pubspec asset declaration first. Release QuickJS eval is FAST (40-100ms per widget incl. 719KB three bootstrap) — the earlier '1.1s eval / double three eval is the boot cost' theory from the Debug harness does NOT apply to Release builds.
