# Note: n_0138_2823

Webcam backdrop repaint FIXED (2026-11-03) + a misdiagnosis corrected: the webcam-lane agent's claim that "dimensions-changing texture upserts don't repaint on GPU" is FALSE — proven by a throwaway Impeller golden probe (16x16 red plane → texture.image swap to 8x6 green → capture: green painted; same-size control blue also painted; sRGB-shifted hues, capture() needs presentedFrames>=4 via a setAnimationLoop that stops before test end or the transient-callback teardown fails the test). Real root cause of the broken stream: the JS pull adapter applied frame 0 by SWAPPING the 16x16 checker image for a camera-sized one mid-stream. Fix (tool/three_example/degrades/webcam_host.mjs): camera.start's grant already carries {width,height} (Swift host knows the preset), so primeCameraDimensions() at grant time installs camera-sized zeroed images on every tracked VideoTexture, sets isVideoTexture=false + userData.jsrVideoElement (exactly the example adapter's degrade bookeeping) so degradeVideoTexture() skips and the 16x16 checker NEVER enters the upsert stream, and dispatches loadedmetadata at prime (aspect/plane scale correct from frame 0). Prime does NOT bump needsUpdate — the zeroed prime is never GPU-submitted; the texture's first upload is camera frame 0 at camera dims, every later upsert is same-size in place. Late-constructed textures are primed in the constructor (primedWidth/Height closure state). The per-frame dims-change resize path stays as the safety net for format changes mid-session. No native_renderer.js change needed. Tests: webcam_host_test.mjs adds resize-at-start + late-texture blocks; js_three_webcam_host_test.dart records per-texture dims across pumps (no 16x16 ever, all 8x6), waits pixel-exact for frame A (the primed 8x6 texture appears in state BEFORE frame A pixels), asserts videoTextures==0 + no 'VideoTexture transport' warn in the camera-present case (fallback case keeps videoTextures==1 + 16x16 + 128 draws = byte-identical promise; prime only runs on granted.available). GOTCHA: prepare.mjs embeds degrades into widget.js with input-sha pins — an edit to webcam_host.mjs DURING a 13-min bulk reprepare produces sha-mismatched embeds (materials-video vs morphtargets pinned DIFFERENT intermediate shas after the race); always re-prepare the affected widgets after the file settles and verify manifest pin == shasum of the degrade file. Also regenerated tool/three/api_matrix.json (prepared 61→303) — was a pre-existing red gate of the uncommitted 303-wave.
