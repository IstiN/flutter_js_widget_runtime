# Note: n_0061_4fc0

js_widget_runtime 0.4.170: NATIVE bytes lane complete. quickjs_runtime 0.3.6 (published, commit 9f9d2e9 — local checkout was 3 commits behind origin, rebase onto 0.3.5 tree) adds `qjs_register_bytes_fn` (C bridge, ~70 lines: JS_GetTypedArrayBuffer + JS_GetArrayBuffer, offset/length validated) + `QuickjsRuntime.registerHostBytesFn(name, cb)` with `hasBytesFn` degrade (same pattern as executePendingJobs; data view is call-scoped — copy if retaining). jsr: QuickJS backend registers `__jsrSendBytes` → `bridge.dispatchBinary`; `jsr.hostCallBinary(name, typedArray)` takes typed arrays directly (subarray views send only visible range), JSC/old-libs auto-fall back to b64 (hostBootstrapJs `__jsrSendBytes = undefined` trick tests the fallback); `jsr.b64encode` encodes the BYTE IMAGE of any typed array (was element-wise truncation — regression tested). Final bench per 60fps frame (100/300/1000 transforms): JSON hostCall 0.93/2.65/8.88 ms → b64 lane 0.28/0.82/2.77 → NATIVE ~0.01/0.02/0.10 ms (88× vs JSON at 1000; bridge gone from profile, remainder is the widget's own Float32Array fill). Gotchas: engine constructors pass config handlers to JsWidgetBridge explicitly; tool/ is NOT in the CI jscpd scan (local-only bench dedup doesn't move the CI number); macOS jscpd measures ~0.11pp BELOW Linux — leave margin. 701 tests, 21/21 widgets, all gates + CI green.
