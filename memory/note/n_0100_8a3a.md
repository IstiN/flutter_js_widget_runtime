# Note: n_0100_8a3a

FIXED (2026-10-30, second attempt — supersedes the earlier double-attach note's fix): the app hang 'Bad state: three.surface: main#1 is already attached' is cured by a CACHED GlobalKey per (engineId, surfaceId) in json_widget_renderer.dart — a static Map<String,Key> _threeSurfaceKeys with putIfAbsent('$engineId/$surfaceId', () => GlobalKey(debugLabel:...)) wrapped as KeyedSubtree around JsThreeNode in _three(). CRITICAL LESSON: the first attempt used GlobalObjectKey('jsr-three/$engineId/$surfaceId') and did NOT work in the app (worked only on the screenshot-harness single boot by luck of timing) — GlobalObjectKey compares its value with identical(), and a freshly interpolated string is a NEW instance every build, so keys never matched, the node remounted on EVERY render (ATTACH#A, ATTACH#B, DETACH#A churn visible via temporary debugPrint instrumentation in js_three_node.dart), and each remount raced the previous state's release → intermittent StateError → error card, presentedFrames stuck. Diagnostics chain that cracked it: example/lib/screenshot.dart + JSR_ISOLATE=1 (real-GPU isolate repro bench), then a debug build of the APP itself (three_example.dart --dart-define=JSR_THREE_EXAMPLE=<id> --debug) run from terminal with ATTACH/DETACH debugPrints — the churn pattern (new state hash per render, new attach before old detach) identified GlobalObjectKey identity failure. Verified: debug app renders webgl_clipping_intersection fully (green sphere + rainbow nested clip planes, calls 16, triangles 33120, frames advancing, zero 'already attached'), full flutter suite +917 green after the FIRST fix and the cached-key fix is the same shape (verify again). Temp instrumentation removed after diagnosis. Note: jsr.exportState REPLACES exported state (probe exports clobber widget keys); Dart RegExp needs literal-prefixed patterns on minified mega-bundles (catastrophic backtrack on unanchored ([\w$]+)= loops).
