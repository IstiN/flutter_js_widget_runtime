# Note: n_0130_39ef

FIXED (2026-11-03 session, supersedes nothing — NEW crash distinct from the 2026-11-02 kill-on-timeout one): app-close SIGABRT (js_widget_runtime_example-2026-11-03-134902.ips, three catalog Release, ~13min) = thread 0 in DartVM::~DartVM → Dart::Cleanup → WaitForIsolateShutdown while thread 48 (the QuickJS isolate-backend worker) was still executing a queued command's pending-job drain (qjs_execute_pending_jobs_capped → promise_reaction_job → qjs_bytes_dispatch → DLRT_GetFfiCallbackMetadata → Assert::Fail). ROOT CAUSE: at VM teardown IsolateCreationEnabled goes false BEFORE WaitForIsolateShutdown returns, so ANY FI trampoline entry FATALs ("GetFfiCallbackMetadata called after shutdown"); the worker dequeues isolate messages sequentially so dispose()'s 'shutdown' command is invisible mid-drain, and one drain can run up to 100k promise reactions (eval auto-drain cap 100k) — seconds of trampoline traffic after dispose began. FIX = COOPERATIVE DRAIN STOP, ordering "stop execution before invalidating receivers": (1) ~/git/quickjs_runtime native/quickjs_bridge.c — process-global atomic g_drain_stop + exports qjs_request_drain_stop/qjs_clear_drain_stop/qjs_drain_stop_requested; BOTH qjs_execute_pending_jobs* loops check it per job and return early leaving jobs pending (close() frees them); .so rebuilt at the checkout path (= $JSR_QUICKJS_LIB target). (2) quickjs_runtime Dart — QuickjsFfi binds the three exports instance-consistently (native-assets @Native when no JSR_QUICKJS_LIB env, DynamicLibrary.open otherwise) with hasDrainStop/requestDrainStop/clearDrainStop/drainStopRequested; QuickjsRuntime pass-throughs. DANGER: binding the exports via a separate DynamicLibrary.open when the runtime uses the hook-built native asset gives TWO g_drain_stop copies (flags silently decouple) — always go through the instance. (3) jsr js_widget_engine_quickjs_isolate_vm.dart — _shutdownWorkerLocked calls _DrainStop.request() BEFORE queuing 'shutdown' and _DrainStop.clear() in a finally after the ack/orphan resolution (process-global: a leaked arm freezes ALL engines' drains; clear in tearDown of tests via debugSetDrainStop). Direct quickjs backend needs no flag (same-isolate deferred close + _isLive guards documented). Tests: ~/git/quickjs_runtime/test/drain_stop_test.dart (4, C contract; FAILS against a pre-flag bridge); jsr test/js_isolate_shutdown_drain_race_test.dart (3; skips with explanation when the bridge predates the fix; validated to FAIL with dispose arming disabled — dispose took 3003ms vs <1500). All isolate/quickjs jsr suites + checkout full suite (109) green. UPSTREAM ASK for quickjs_runtime 0.4.9: publish from this checkout so the app (which builds the bridge from pub-cache sources via the code-assets hook) gets the flag; the .so patch reaches only dynamic-library consumers (tests) until then. RESIDUAL WINDOW (documented, needs JS_SetInterruptHandler upstream): a worker stuck inside one synchronous JS_Eval (huge boot eval / infinite loop) can't be interrupted by the flag; VM teardown during THAT window can still hit the FATAL family.
