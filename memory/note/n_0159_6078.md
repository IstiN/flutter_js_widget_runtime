# Note: n_0159_6078

R1 shadow lane DOES render DRAW_BATCH casters — proven end-to-end in the real macOS app (2026-11-05): synthetic widget (BatchedMesh 6 boxes castShadow + DirectionalLight + ground receiveShadow + shadowMap.enabled) → diagnostics renderedShadowDraws:2 (batch draw + control Mesh), shadowMap 1024x1024, shadowCacheHits 247, and the PNG capture (/tmp/batch-shadow-app.png) shows all six batch boxes casting ground shadows. CORRECTION to the earlier task premise: upstream r186 examples/webgl_batch_lod_bvh.html has NO shadows at all (no shadowMap.enabled, no lights, no ground — scene is PMREM RoomEnvironment + BatchedMesh only; the widget's original.html is byte-identical to upstream, sha 4bdcb5a0). So three-batch-lod-bvh renderedShadowDraws:0 is CORRECT official parity, not a lost config; shadows stay disabled. In-flutter-test GPU capture is broken on this machine for ALL goldens (backendReady stuck 0, e.g. js_three_r1_point_shadow_golden_test with JSR_THREE_GPU_GOLDEN=true fails the same way) — shadow/fps evidence must come from a real app run: example/lib/probe_fps.dart (JSR_WIDGET/JSR_WIDGET_PATH/JSR_OUT/JSR_STORM/JSR_NO_STUB/JSR_SKIP_RAYCAST) boots any widget incl. synthetic disk-loaded ones (must call jsr.render({type:'three',canvasId:'main'}) to mount — the raw-lane gotcha: no jsr.render call = presentedFrames stays 0).
