# Note: n_0159_5aa5

webgl_batch_lod_bvh interactive-fps fix LANDED (uncommitted, 2026-11-05): the R1 BatchedMesh proxy lane in tool/three/src/native_renderer.js stubs proxy.raycast to a no-op (jsrBatchedMeshProxyRaycast; proxies keep userData.jsrBatchedMeshProxy). Bundle sha 014ec93c contains it (minified `x.raycast=vw`); all 303 prepared widgets reprepare byte-stable (the runtime bundle is pinned per-widget but not embedded). MEASURED in-app (example/lib/probe_fps.dart, release build, presentedFps windows): static 119.8-119.9; pointermove storm WITH stub 23.5fps at ~40Hz achievable dispatch (21.9ms/event); JSR_NO_STUB=1 control (re-arms default InstancedMesh raycast on proxies) 6.9fps at 14Hz (70ms/event) — matches the previously tested 120→0-4 collapse at 125Hz. ATTRIBUTION: JSR_SKIP_RAYCAST=1 (short-circuits Raycaster.intersectObject) holds 120.3fps at TRUE 125Hz (249 events/2s, 0.13ms/dispatch) — with the stub, proxies cost zero; the ONLY residual storm cost is the official module's own BVH hover raycast (~22ms/event in QuickJS), kept intentionally (task scope: keep the module's BVH path). So "fps >=60 under 125Hz pointermove" is only met when the official hover lane is excluded; the proxy-storm component is fully gone. Committed regression: test/js_three_batch_lod_interactive_fps_test.dart (stub-behavior assertions via Object3D.add wrap + Raycaster.intersectObject counter + storm frame-flow/40ms-per-event bounds; harness numbers: 150 events → 30/30 frames submitted, 11.0ms/event overhead).
