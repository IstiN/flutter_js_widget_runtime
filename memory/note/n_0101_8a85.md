# Note: n_0101_8a85

FIXED (2026-10-30): R1 clipping-plane SIGN bug — webgl_clipping rendered EMPTY with Local Clipping enabled (entire spheres discarded; only the ground/background visible), objects reappeared only when the user unchecked Enabled. Root cause: the protocol carries three.js Plane constants verbatim (unit normal XYZ + constant, js_three_protocol.dart JsThreeClippingUpsert), and the R1 shaders (shaders/three_r1.frag applyClipping + three_r1_shadow.frag) discard where `dot(normal, worldPosition) < w` — but the GPU binding (three_gpu_uniforms.dart _threeClippingUniform) wrote the RAW constant as w instead of the NEGATED one. three.js keeps the `normal·p + constant >= 0` half-space, i.e. discard where `dot(n,p) < -constant`. Fix: write -set.planes[offset+3] in _threeClippingUniform (single place; the shadow pass shares this builder via _bindShadowClipping). Verified visually via the screenshot harness: three-clipping now shows the official look (green torus knots on the gray floor with flat sliced tops from localPlane (0,-1,0,0.8); presentedFrames 899). Test updated: test/js_three_draw_plan_test.dart 'v3 spot lights and clipping sets pack exact GPU uniforms' now asserts the negated constant (-0.1) with a comment pining the three.js half-space semantics — ANY future change must keep protocol bytes = raw three.js constants and only negate at the GPU boundary. Lesson: wave-1 clipping tests asserted PROTOCOL fields (hasClipping, plane counts) but never the visual half-space semantics — protocol-green does not mean pixel-correct for shader-side math; visual modules (clipping, shadows, tone mapping) need at least one screenshot-harness look per module.
