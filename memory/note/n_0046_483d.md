# Note: n_0046_483d

js_widget_runtime 0.4.128 published (commit dabfd87): `jsr.capture(opts?)` — widgets self-screenshot their rendered tree from inside JS; core bridge channel `__jsr_capture` + optional JsRuntimeConfig.captureHandler; hosts without one reject (voxel.attach-style degradation). The jsr_widget CLI implements it: `--capture-dir <dir>` + report `captures[]`; the agent harness (bot) can now self-screenshot via `jsr_widget test` alone. Two hard-won engine lessons baked into the design: (1) the capture channel MUST be fire-and-forget at the bridge level — an awaited channel whose handler future is held pending (across a test phase) starves `__jsr_event_done` and wedges every subsequent callEvent; (2) resolving a pending JS promise from inside the testWidgets (fake-async) zone re-enters the QuickJS runtime from a native-callback context and deadlocks the isolate in a synchronous FFI eval — the CLI resolves IMMEDIATELY with the future path (voxel.mesh sync pattern) and rasterizes later. Flutter-test lesson: engine boot + Future.delayed settles must run in plain tests (real event loop); only pump/captureImage belongs in testWidgets (a Future.delayed in a testWidgets body never ticks without pump). CRAP-12 ratchet forced parseJsrToolArgs → handler-map table (flag→_FlagHandler lambdas, main loop CC ~6) and defaultQuickjsLibEnv → _newestBuiltBridge(cacheRoot, env) decomposition — when a coverage-starved function fails the ratchet, decompose AND write tests (silent python no-op replaces on tests cost an hour: verify edits landed with grep before running the suite).
